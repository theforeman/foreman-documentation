1. Install Satellite Server

Use the following procedures to install Satellite Server in a connected environment, perform the initial configuration, and import subscription manifests.

When you install Satellite Server from a connected network, you can obtain packages and receive updates directly from the Red Hat Content Delivery Network.

You can deploy Satellite Server with a default internal database or with an external database.

Note

You cannot register Satellite Server to itself.

1.1. Satellite Server installation planning

Before installing Satellite Server, review the operating system requirements, system requirements, storage requirements, and network requirements to ensure your environment meets the specifications.

1.1.1. Operating system requirements

Ensure that your operating system and installation method meet the necessary requirements before you install Satellite.

You can deploy Satellite on the following operating systems:

  • Red Hat Enterprise Linux 10 (x86_64)

You can install the operating system from a disc, local ISO image, Kickstart, or any other method that Red Hat supports.

Use the latest version of Red Hat Enterprise Linux 10 available at the time of installation. Previous versions of Red Hat Enterprise Linux including EUS or z-stream are not supported.

Red Hat Red Hat Satellite requires a Red Hat Enterprise Linux installation with the @Base package group with no other package-set modifications, and without third-party configurations or software not directly necessary for the direct operation of the server. This restriction includes hardening and other non-Red Hat security software. If you require such software in your infrastructure, install and verify a complete working Red Hat Satellite first, then create a backup of the system before adding any non-Red Hat software.

1.1.2. System requirements

System requirements for Red Hat Satellite include minimum CPU, RAM, storage, hostname format, SELinux configuration, and time synchronization to ensure proper installation and operation.

Red Hat Satellite is fully supported on both physical systems and virtual machines that run on hypervisors that are supported to run Red Hat Enterprise Linux. For more information about certified hypervisors, see Certified Guest Operating Systems in Red Hat OpenStack Platform, Red Hat Virtualization, Red Hat OpenShift Virtualization and Red Hat Enterprise Linux with KVM.

Follow these system requirements when installing Red Hat Satellite:

  • Install Red Hat Satellite on a freshly provisioned system that serves no other function except to run Red Hat Satellite. Do not use an existing system because satellitectl affects the configuration of several components.

  • Ensure you have administrative user (root) access to the system.

  • Ensure the system meets the following requirements:

    • 4 CPU cores

    • 20 GB RAM or higher

    • 4 GB RAM of swap space or higher

    • A unique host name, which can contain lower-case letters, numbers, dots (.) and hyphens (-)

  • If you use custom certificates, ensure that the Common Name (CN) of the custom certificate is a fully qualified domain name (FQDN). Satellite Server and Capsule Server do not support shortnames in the hostnames.

  • Ensure SELinux is enabled, either in enforcing or permissive mode. Installation with disabled SELinux is not supported. For more information, see Security considerations.

  • Ensure the system clock on the system is synchronized across the network. If the system clock is not synchronized, SSL certificate verification might fail. For example, you can use the Chrony suite for timekeeping. For more information, see Red Hat Enterprise Linux 10 Configuring time synchronization.

  • If you are installing in an environment with air-gapped Satellite Servers with Inter-Satellite Synchronization, ensure that all your Satellite Servers are on the same Satellite version for ISS Export Sync to work. ISS Network Sync works across all Satellite versions that support it. For more information, see Synchronize content between Satellite Servers.

  • Ensure the system uses the UTF-8 encoding. If your territory is USA and your language is English, set en_US.utf-8 as the system-wide locale settings. For more information about configuring system locale in Red Hat Enterprise Linux, see Configuring the system locale in Red Hat Enterprise Linux 10 Interactively installing RHEL from installation media.

  • If you use an external identity provider in your deployment, ensure that the provider did not create the apache user account on the system. This user account can cause conflicts with the local users that Red Hat Satellite creates.

1.1.3. Storage requirements

Your system must meet the following storage requirements before you can install Satellite Server.

Follow these storage requirements when installing Satellite Server:

  • Ensure that the directories used by Satellite Server have sufficient disk space available:

    Table 1. Minimum storage requirements for a Satellite Server installation
    Directory Installation Size Runtime Size

    /var/log

    10 MB

    10 GB

    /var/lib/pgsql

    1 GB

    20 GB

    /usr

    10 GB

    Not Applicable

    /var/lib/pulp

    1 MB

    300 GB

    /var/lib/containers

    20 GB

    30 GB

    These values are based on expected use case scenarios and can vary according to individual environments. Because disk usage grows over time, monitor these partitions and expand them as required. To make expanding storage easier, use Logical Volume Manager (LVM) for these volumes.

  • If you mount the /var/lib/pulp directory as an NFS share, specify the SELinux context of the /var/lib/pulp directory in the file system table. Add the following lines to /etc/fstab:

    nfs.example.com:/nfsshare  /var/lib/pulp  nfs  context="unconfined_u:object_r:var_lib_t:s0"  1 2

    If the NFS share is already mounted, remount it using the above configuration and restore the SELinux context:

    # restorecon -R /var/lib/pulp

    Do not use symbolic links for /var/lib/pulp/.

  • Disk partitions in Red Hat Enterprise Linux 10 Managing storage devices

1.1.4. Best practices for optimizing storage

You can optimize your storage by following the storage best practices. These include using LVM for /var, high-bandwidth storage for critical directories, and appropriate file systems to improve I/O performance and scalability.

  • The exact amount of storage you require for log messages depends on your installation and setup. You can manage the size of the log files by using logrotate.

  • Consider mounting /var on LVM storage. This can help the system to scale because most Red Hat Satellite data is stored in the /var directory.

  • Use high-bandwidth, low-latency storage for the /var/lib/pulp/ and /var/lib/pgsql directories. Using high latency, low-bandwidth storage causes performance degradation because Red Hat Satellite has many operations that are I/O intensive.

  • Use a file system with low input-output latency. Do not use the GFS2 file system because the input-output latency is too high.

1.1.5. IPv4 and IPv6 requirements

You can install Satellite in an IPv4 network or in an IPv6 network. Your system must meet the following requirements for a successful installation and operation.

Note

Dual-stack Satellite installations that use both IPv4 and IPv6 are not supported.

The following requirements apply to installations in an IPv4 network:

  • Ensure an IPv6 loopback is configured on the base system. The loopback is typically configured by default. Do not disable it. Using the ipv6.disable=1 kernel parameter or the net.ipv6.conf.lo.disable_ipv6 = 1 sysctl option will break the installation.

The following requirements apply to installations in an IPv6 network:

  • Deploy an external HTTP proxy server that supports both IPv4 and IPv6. This is required because Red Hat Content Delivery Network distributes content only over IPv4 networks, therefore you must use this HTTP proxy to pull content into the Satellite on your IPv6 network. You must configure Satellite to use this dual-stack (supporting both IPv4 and IPv6) HTTP proxy as the default HTTP proxy.

  • Satellite does not support configuring an HTTP proxy using a direct IPv6 address. Instead, configure the HTTP proxy with a FQDN that resolves to the IPv6 address.

If you intend to provision hosts in an IPv6 network, the following requirements also apply:

  • Deploy an external DHCPv6 server and configure it manually to communicate with the network boot process and to manage IP address assignment because Satellite cannot integrate with a DHCPv6 server and manage its configuration. For more information about DHCPv6 server configuration, see Options in unmanaged DHCPv6.

  • Configure Satellite for UEFI HTTP boot provisioning. Although Satellite provisioning templates include IPv6 support for PXE and HTTP (iPXE) provisioning, the UEFI HTTP Boot provisioning is the only tested and certified provisioning workflow.

  • Create EBS volumes for directories expected to contain larger amounts of data like /var/lib/pulp and ensure they are correctly mounted on start-up and before continuing the installation.

  • Optional: Store other data on a separate EBS volume.

  • If you want Satellite Server and Capsule Server to communicate using external DNS hostnames, open the required ports for communication in the AWS Security Group that is associated with the instance.

1.2. Environment preparation for Satellite Server installation

Prepare your environment for Satellite Server installation by opening required network ports, verifying DNS resolution, and configuring repositories.

1.2.1. Open required ports

Open the required network ports to enable communication between Satellite components across your infrastructure, including firewall configurations for both host-based and network-based firewalls.

Note

Some cloud solutions must be specifically configured to allow communications between machines because they isolate machines similarly to network-based firewalls. If you use an application-based firewall, ensure that the application-based firewall permits all applications that are listed in the tables and known to your firewall. If possible, disable the application checking and allow open port communication based on the protocol.
Procedure

  1. Open the ports for clients on Satellite Server:

    # firewall-cmd \
--add-port="8000/tcp" \
--add-port="8443/tcp"

  2. Allow access to services on Satellite Server:

    # firewall-cmd \
--add-service=http \
--add-service=https

  3. Make the changes persistent:

    # firewall-cmd --runtime-to-permanent
Verification

  • View all firewall zones and allowed services:

    # firewall-cmd --list-all
Additional resources

  • Networking considerations in Satellite

  • Using and configuring firewalld in Red Hat Enterprise Linux 10 Configuring firewalls and packet filters

1.2.2. Verify DNS resolution

Verify the full forward and reverse DNS resolution using a fully-qualified domain name to prevent issues while installing Satellite.

Procedure

  1. Ensure that the host name and local host resolve correctly:

    # ping -c1 localhost
# ping -c1 `hostname -f` # my_system.domain.com

    Successful name resolution results in output similar to the following:

    # ping -c1 localhost
PING localhost (127.0.0.1) 56(84) bytes of data.
64 bytes from localhost (127.0.0.1): icmp_seq=1 ttl=64 time=0.043 ms

--- localhost ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 0.043/0.043/0.043/0.000 ms

# ping -c1 `hostname -f`
PING hostname.gateway (XX.XX.XX.XX) 56(84) bytes of data.
64 bytes from hostname.gateway (XX.XX.XX.XX): icmp_seq=1 ttl=64 time=0.019 ms

--- localhost.gateway ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 0.019/0.019/0.019/0.000 ms

  2. To avoid discrepancies with static and transient host names, set all the host names on the system by entering the following command:

    # hostnamectl set-hostname name
    Warning

    Name resolution is critical to the operation of Satellite. If Satellite cannot properly resolve its fully qualified domain name, tasks such as content management, subscription management, and provisioning will fail.

1.2.4. Register to Red Hat Subscription Management

Registering the host to Red Hat Subscription Management enables the host to subscribe to and consume content for any subscriptions available to the user. This includes content such as Red Hat Enterprise Linux and Red Hat Satellite.

Procedure

  • Register your system with the Red Hat Content Delivery Network, entering your Customer Portal user name and password when prompted:

    # subscription-manager register

    The command displays output similar to the following:

    # subscription-manager register
Username: user_name
Password:
The system has been registered with ID: 541084ff2-44cab-4eb1-9fa1-7683431bcf9a

1.2.5. Configure repositories for Satellite

Enable the necessary repositories on your Satellite host to access installation packages and dependencies.

Procedure

  1. Disable all repositories:

    # subscription-manager repos --disable "*"

  2. Enable the following repositories:

    # subscription-manager repos \
--enable=rhel-10-for-x86_64-baseos-rpms \
--enable=rhel-10-for-x86_64-appstream-rpms \
--enable=satellite-6.20-for-rhel-10-x86_64-rpms
Verification

  • Verify that the required repositories are enabled:

    # dnf repolist enabled

1.2.6. Log in to the Red Hat container registry

You must log in to the Red Hat container registry so that the host can consume container images needed for the deployment of Satellite.

Procedure

  1. Install Podman:

    # dnf install podman

  2. Log in to the Red Hat container registry by using Podman:

    # podman login --authfile /etc/foreman/registry-auth.json registry.redhat.io

    This command creates the /etc/foreman/registry-auth.json file.

1.3. Deploy Satellite Server configuration with the default database

You can deploy a Satellite Server in a default configuration by using the satellitectl deploy command.

To extend the default deployment, you can select one or more features or add one or more configuration options.

The initial deployment also installs PostgreSQL databases on the same server.

Note

Any additional run of the satellitectl deploy command recreates configuration files used by the Satellite services based on the parameters given in this and previous runs. This way, you can add additional settings to your deployment or change previous configurations.

For more information on how to apply custom configuration on other services, see Perform additional configuration on Satellite Server.
Prerequisites

  • Your system conforms with the requirements. For more information, see Satellite Server installation planning.

  • Your system is prepared for the installation. For more information, see Environment preparation for Satellite Server installation.

Procedure

  1. Install the satellitectl package:

    # dnf install satellitectl

  2. Update the system to the latest available version:

    # dnf upgrade

  3. Optional: Inspect the features available for deployment:

    # satellitectl features

    You can enable one or more features by adding the --add-feature Feature-1 --add-feature Feature-2 option to the satellitectl deploy command.

  4. Deploy the configuration on the server:

    # satellitectl deploy --flavor satellite \
--initial-admin-username My_Admin_User_Name \
--initial-admin-password My_Admin_Password \
--initial-organization "My_Organization" \
--initial-location "My_Location"
    Note

    The options prefixed with initial- affect only new databases.

    Specify a meaningful value for the initial-organization option. This can be your company name. The satellitectl tool creates an internal label that matches the value, and you cannot change it later. If you do not specify a value, an organization called Default Organization with the label Default_Organization is created. You can rename the organization name but not the label.

1.4. Deploy Satellite Server configuration with an external database

By default, the Satellite deployment includes installing a PostgreSQL database on the same host as Satellite Server. However, in certain Satellite deployments, using external databases instead of the default local databases can help with the server load or have other benefits.

To extend the default deployment, you can select one or more features or add one or more configuration options.

Note

Any additional run of the satellitectl deploy command recreates configuration files used by the Satellite services based on the parameters given in this and previous runs. This way, you can add additional settings to your deployment or change previous configurations.

For more information on how to apply custom configuration on other services, see Perform additional configuration on Satellite Server.
Prerequisites

  • You have considered whether using an external database is beneficial for your use case. For more information, see PostgreSQL as an external database considerations.

  • PostgreSQL is installed on an external database host you prepared. For more information, see Install PostgreSQL as an external database.

  • Your system conforms with the requirements. For more information, see Satellite Server installation planning.

  • Your system is prepared for the installation. For more information, see Preparing environment for Satellite Server installation.

Procedure

  1. Install the satellitectl package:

    # dnf install satellitectl

  2. Update the system to the latest available version:

    # dnf upgrade

  3. Optional: Inspect the features available for deployment:

    # satellitectl features

    You can enable one or more features by adding the --add-feature Feature-1 --add-feature Feature-2 option to the satellitectl deploy command.

  4. Deploy the configuration on the server:

    # satellitectl deploy --flavor satellite \
--initial-admin-username My_Admin_User_Name \
--initial-admin-password My_Admin_Password \
--initial-organization "My_Organization" \
--initial-location "My_Location" \
--database-mode external \
--database-host My_Database_Host \
--database-port My_Database_Port \
--database-ssl-mode {disable,allow,prefer,require,verify-ca,verify-full} \
--database-ssl-ca My_Database_SSL_CA \
--candlepin-database-name My_Candlepin_Database_Name \
--candlepin-database-password My_Candlepin_Database_Password \
--candlepin-database-user My_Candlepin_Database_User \
--pulp-database-name My_Pulp_Database_Name \
--pulp-database-password My_Pulp_Database_Password \
--pulp-database-user My_Pulp_Database_User \
--foreman-database-name My_Foreman_Database_Name \
--foreman-database-user My_Foreman_Database_User \
--foreman-database-password My_Foreman_Database_Password
    Note

    The options prefixed with initial- affect only new databases.

    Specify a meaningful value for the initial-organization option. This can be your company name. The satellitectl tool creates an internal label that matches the value, and you cannot change it later. If you do not specify a value, an organization called Default Organization with the label Default_Organization is created. You can rename the organization name but not the label.

1.5. Red Hat subscription manifests in Satellite

You can import a Red Hat subscription manifest into Satellite to provide subscription allocation to your organization in Satellite.

Note

Simple Content Access (SCA) is set on the organization, not the manifest. Importing a manifest does not change your organization’s Simple Content Access status.

Simple Content Access simplifies the subscription experience for administrators.

Additional resources

  • Subscription Management Administration Guide for Red Hat Enterprise Linux on the Red Hat Customer Portal

1.5.1. Obtain a Red Hat subscription manifest

You can create and export a Red Hat subscription manifest to prepare subscriptions for import into Satellite.

Procedure

  • Export your Red Hat subscription manifest from the Red Hat Hybrid Cloud Console. For more information, see Creating and managing manifests for a connected Satellite Server in Subscription Central.

1.5.2. Import a Red Hat subscription manifest by using Satellite web UI

You can import a Red Hat subscription manifest into Satellite Server by using Satellite web UI. Import the manifest so that you can enable and synchronize Red Hat repositories in your organization.

Prerequisites

  • You have a Red Hat subscription manifest file. For more information, see Obtain a Red Hat subscription manifest.

Procedure

  1. In the Satellite web UI, ensure that the context is set to the organization you want to use.

  2. Navigate to Content > Subscriptions.

  3. Click the More actions icon, and then select Manage Manifest.

  4. In the Manage Manifest window, click Choose File.

  5. Navigate to the location that contains the Red Hat subscription manifest file and click Open.

1.5.3. Import a Red Hat subscription manifest by using Hammer CLI

You can import a Red Hat subscription manifest into Satellite Server by using Hammer CLI. Import the manifest so that you can enable and synchronize Red Hat repositories in your organization.

Prerequisites

  • You have a Red Hat subscription manifest file. For more information, see Obtain a Red Hat subscription manifest.

Procedure

  1. Copy the Red Hat subscription manifest file from your local machine to Satellite Server:

    $ scp ~/manifest_file.zip root@satellite.example.com:~/.

  2. Log in to Satellite Server over SSH as the root user.

  3. Import the Red Hat subscription manifest file:

    $ hammer subscription upload \
--file ~/manifest_file.zip \
--organization "My_Organization"

In the largest Satellite environments, the size of /var/lib/pgsql on Capsule Server can grow to double or triple the size of /var/lib/pgsql on your Satellite Server.

2.1.4. Open required ports

Open the required network ports to enable communication between Satellite components across your infrastructure, including firewall configurations for both host-based and network-based firewalls.

Note

Some cloud solutions must be specifically configured to allow communications between machines because they isolate machines similarly to network-based firewalls. If you use an application-based firewall, ensure that the application-based firewall permits all applications that are listed in the tables and known to your firewall. If possible, disable the application checking and allow open port communication based on the protocol.
Procedure

  1. Open the ports for clients on Satellite Server:

    # firewall-cmd \
--add-port="8000/tcp" \
--add-port="8443/tcp"

  2. Allow access to services on Satellite Server:

    # firewall-cmd \
--add-service=http \
--add-service=https

  3. Make the changes persistent:

    # firewall-cmd --runtime-to-permanent
Verification

  • View all firewall zones and allowed services:

    # firewall-cmd --list-all

Verify the full forward and reverse DNS resolution using a fully-qualified domain name to prevent issues while installing Satellite.

2.1.6. Best practices for optimizing storage

You can optimize your storage by following the storage best practices. These include using LVM for /var, high-bandwidth storage for critical directories, and appropriate file systems to improve I/O performance and scalability.

  • The exact amount of storage you require for log messages depends on your installation and setup. You can manage the size of the log files by using logrotate.

  • Consider mounting /var on LVM storage. This can help the system to scale because most Red Hat Satellite data is stored in the /var directory.

  • Use high-bandwidth, low-latency storage for the /var/lib/pulp/ and /var/lib/pgsql directories. Using high latency, low-bandwidth storage causes performance degradation because Red Hat Satellite has many operations that are I/O intensive.

  • Use a file system with low input-output latency. Do not use the GFS2 file system because the input-output latency is too high.

2.1.7. Serve Capsule container images from Satellite Server

A Capsule Server pulls its container images through your Satellite Server instead of directly from registry.redhat.io. On your Satellite Server, synchronize the required container images before you install Capsule Server, so that Satellite Server can serve them to the Capsule.

Note

Skip this procedure if you install the Capsule Server from an ISO image.
Prerequisites

  • A Red Hat registry service account to authenticate the synchronization against registry.redhat.io. For more information, see Red Hat Container Registry Authentication.

Procedure

  1. On your Satellite Server, create a product to contain all Capsule container images:

    $ hammer product create \
--name "Capsule Container Images" \
--organization "My_Organization"

    With the default registry name pattern of <organization>/<product>/<repository>, the published registry path uses the lowercased labels of your organization and product, for example my_organization/capsule_container_images/<repository>. For more information, see Configure container registry name patterns for a lifecycle environment.

  2. On your Satellite Server, create a container repository for each required image. Each repository name must match the final path component of the upstream image, and the tags must match the tags that the Capsule requests, or the image pull fails:

    $ hammer repository create \
--name "foreman-proxy-rhel10" \
--product "Capsule Container Images" \
--organization "My_Organization" \
--content-type "docker" \
--url "https://registry.redhat.io" \
--docker-upstream-name "satellite/foreman-proxy-rhel10" \
--include-tags "6.20" \
--upstream-username "My_Service_Account_Username" \
--upstream-password "My_Service_Account_Token"

$ hammer repository create \
--name "pulp-rhel10" \
--product "Capsule Container Images" \
--organization "My_Organization" \
--content-type "docker" \
--url "https://registry.redhat.io" \
--docker-upstream-name "satellite/pulp-rhel10" \
--include-tags "6.20" \
--upstream-username "My_Service_Account_Username" \
--upstream-password "My_Service_Account_Token"

$ hammer repository create \
--name "postgresql-16" \
--product "Capsule Container Images" \
--organization "My_Organization" \
--content-type "docker" \
--url "https://registry.redhat.io" \
--docker-upstream-name "rhel10/postgresql-16" \
--include-tags "latest" \
--upstream-username "My_Service_Account_Username" \
--upstream-password "My_Service_Account_Token"

$ hammer repository create \
--name "valkey-8" \
--product "Capsule Container Images" \
--organization "My_Organization" \
--content-type "docker" \
--url "https://registry.redhat.io" \
--docker-upstream-name "rhel10/valkey-8" \
--include-tags "latest" \
--upstream-username "My_Service_Account_Username" \
--upstream-password "My_Service_Account_Token"

  3. On your Satellite Server, synchronize the product to download the container images to your Satellite Server:

    $ hammer product synchronize \
--name "Capsule Container Images" \
--organization "My_Organization"

    The synchronized content is available in the Library environment through the Default Organization View. When you register the Capsule with an activation key that assigns the Library environment and the Default Organization View, you do not need to publish or promote a content view for the Capsule to pull these images.

Verification

  • Confirm that the container images are published on your Satellite Server:

    $ curl --cacert /var/lib/foremanctl/certs/certs/ca-bundle.crt --silent --user admin \
https://satellite.example.com/v2/_catalog

    The output lists the four repositories under your product path, for example:

    my_organization/capsule_container_images/foreman-proxy-rhel10
my_organization/capsule_container_images/pulp-rhel10
my_organization/capsule_container_images/postgresql-16
my_organization/capsule_container_images/valkey-8
Next steps

  • Configure the Capsule to pull its container images from the product path, for example, my_organization/capsule_container_images. For more information, see Configure Capsule Server to pull container images from Satellite Server.

2.2. Prerequisites for registering Capsule Server to Satellite Server

Your environment must meet the following requirements before you can register your Capsule Server to your Satellite Server.

  • Prerequisites for Red Hat subscription manifest:

    • On Satellite Server, a manifest must be installed and it must contain the appropriate repositories for the organization you want Capsule to belong to.

    • The manifest must contain repositories for the base operating system on which you want to install Capsule, as well as any clients that you want to connect to Capsule.

    • The repositories must be synchronized.

      For more information on manifests and repositories, see Managing Red Hat Subscriptions.

  • Prerequisites for host registration:

    • An activation key to assign to your Capsule during registration. The activation key attaches a lifecycle environment and a content view to the Capsule. For more information, see Create an activation key by using Satellite web UI.

      If you serve the Capsule container images from the Library environment through the Default Organization View, assign the Library environment and the Default Organization View to the activation key.

  • Prerequisites for HTTP proxy and network:

    • The Satellite Server base operating system must be able to resolve the host name of the Capsule base operating system and vice versa.

    • Ensure HTTPS connection using client certificate authentication is possible between Capsule Server and Satellite Server. HTTP proxies between Capsule Server and Satellite Server are not supported.

    • You must configure the host and network-based firewalls accordingly.

2.5. Configure Capsule Server to pull container images from Satellite Server

On your Capsule Server, authenticate to the Satellite Server container registry and redirect container image pulls to your Satellite Server, so that the Capsule pulls its container images through Satellite Server instead of from registry.redhat.io.

Prerequisites

  • You have synchronized the Capsule container images to your Satellite Server. For more information, see Serve Capsule container images from Satellite Server.

  • If Satellite Server uses a self-signed certificate, you have configured Podman on the Capsule to trust the Satellite Server certificate authority.

Procedure

  1. On your Capsule Server, log in to the Satellite Server container registry. Store the credentials in the authentication file that the Capsule uses to pull its container images:

    # podman login --authfile /etc/foreman/registry-auth.json satellite.example.com

    Enter your Satellite username and password. This is a one-time interactive login: every later image pull, including the deployment in the following steps, reads this authentication file, so you do not need to log in again.

    Important

    Because image pulls are redirected to your Satellite Server, use your Satellite Server credentials, not your registry.redhat.io credentials.

    Optional: Confirm that the login succeeded and that Satellite Server serves the Capsule container images:

    # podman search satellite.example.com/

  2. On your Capsule Server, create the registry mirror configuration file /etc/containers/registries.conf.d/50-foremanctl-mirror.conf with one [[registry]] block per image namespace. Point each block at your product path on Satellite Server:

    [[registry]]
prefix = "registry.redhat.io/satellite"
location = "satellite.example.com/My_Organization_Label/capsule_container_images"

[[registry]]
prefix = "registry.redhat.io/rhel10"
location = "satellite.example.com/My_Organization_Label/capsule_container_images"

    Use the shared product path that you noted when you synchronized the container images to your Satellite Server.

Verification

  • Pull one image for each prefix and confirm that the image comes from your Satellite Server:

    # podman pull --log-level debug --authfile /etc/foreman/registry-auth.json registry.redhat.io/rhel10/postgresql-16:latest

    In the Trying to access line of the output, verify that the source is your Satellite Server, not registry.redhat.io.

2.6. Configure Capsule Server with a default SSL certificate

If your Satellite Server is configured with the default certificate, you must configure your Capsule Server with the SSL certificate that is signed by Satellite Server default Certificate Authority (CA).

Prerequisites

  • Capsule Server is registered to Satellite Server. For more information, see Register Capsule Server.

  • Capsule Server packages are installed. For more information, see Install Capsule packages.

  • The required ports are open. For more information, see Open required ports.

Procedure

  1. On your Satellite Server, generate an authentication bundle for the Capsule Server:

    # satellitectl auth-bundle capsule.example.com

    To regenerate the bundle for an existing Capsule Server, add the --certificate-renew option to the satellitectl auth-bundle command.

  2. On your Satellite Server, copy the authentication bundle to Capsule Server:

    # scp /var/lib/foremanctl/certs/bundles/capsule.example.com.tar.gz \
root@capsule.example.com:/root/capsule.example.com.tar.gz
    Important

    The authentication bundle contains TLS private keys and OAuth credentials. Treat the bundle as highly sensitive and delete any copies after deployment.

  3. On the Capsule Server, deploy the configuration:

    # satellitectl deploy-proxy \
--flavor capsule \
--auth-bundle /root/capsule.example.com.tar.gz \
--foreman-fqdn satellite.example.com

2.7. Recognize host IP addresses behind Capsule Server

Add your Capsule Server to the list of trusted proxies on Satellite Server so that Satellite records the real IP address of hosts that register or are provisioned through your Capsule Server.

When hosts register or are provisioned through a Capsule Server, their requests reach Satellite Server through the Capsule. Satellite reads the client IP address from the X-Forwarded-For HTTP header that Capsule sets. For security reasons, Satellite recognizes this header only from trusted proxies.

Procedure

  1. On Satellite Server, add your Capsule Server to the list of trusted proxies:

    # satellitectl deploy \
--foreman-trusted-proxy My_Proxy_IP_address

    Enter all IPv4 and IPv6 addresses of your Capsule Server, or a network range in CIDR notation. To trust more than one proxy, repeat the --foreman-trusted-proxy option for each address or range.

    The command adds the address to the list of trusted proxies that is already stored, so you do not have to repeat entries that you added earlier. The localhost ranges 127.0.0.0/8 and ::1 are always trusted and you do not need to add them.

    Warning

    Trust only the specific addresses or the narrowest possible ranges of your Capsules. Satellite accepts the X-Forwarded-For header from any source within a trusted range. Therefore, a client within the range might forge this header to bypass IP-based access controls or falsify the host IP addresses that Satellite records.

  2. Optional: Remove an address or range from the list of trusted proxies:

    # satellitectl deploy \
--foreman-trusted-proxy-remove My_Proxy_IP_address

    You cannot remove the localhost ranges 127.0.0.0/8 and ::1.

2.8. Assign organization and location to Capsule Server

Assign the correct organization and location to Capsule Server to properly manage your Capsule Server within your organizational structure.

Note

Assigning a Capsule to the same location as your Satellite Server with an embedded Capsule prevents Red Hat Lightspeed from uploading the Red Hat Lightspeed inventory. To enable the inventory upload, synchronize SSH keys for both Capsules.
Prerequisites

  • Your user account has the assign_organizations and assign_locations permissions.

  • You belong to the organization and location that you want to assign to the Capsule.

Procedure

  1. Log into the Satellite web UI.

  2. From the Organization list in the upper-left of the screen, select Any Organization.

  3. From the Location list in the upper-left of the screen, select Any Location.

  4. In the Satellite web UI, navigate to Hosts > All Hosts and select Capsule Server.

  5. From the options menu, select Change associations > Organization.

  6. Select the organization where you want to assign this Capsule.

  7. Select Fix on mismatch.

  8. Click Change organization.

  9. From the options menu, select Change associations > Location.

  10. Select the location where you want to assign this Capsule.

  11. Select Fix on mismatch.

  12. Click Change location.

  13. In the Satellite web UI, navigate to Administer > Organizations and click the organization to which you have assigned Capsule.

  14. Click Capsules tab and ensure that Capsule Server is listed under the Selected items list, then click Submit.

  15. In the Satellite web UI, navigate to Administer > Locations and click the location to which you have assigned Capsule.

  16. Click Capsules tab and ensure that Capsule Server is listed under the Selected items list, then click Submit.

Verification

Optionally, you can verify if Capsule Server is correctly listed in the Satellite web UI.

  1. Select the organization from the Organization list.

  2. Select the location from the Location list.

  3. In the Satellite web UI, navigate to Hosts > All Hosts.

  4. In the Satellite web UI, navigate to Infrastructure > Capsules.

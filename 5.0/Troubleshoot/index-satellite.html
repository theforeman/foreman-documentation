1. Troubleshoot installation issues

Diagnose and identify root causes when Satellite installation fails or stalls to resolve issues and complete installation successfully.

1.1. Resolve 403 errors from host header checks

If you receive a 403 Forbidden error when connecting to Satellite Server by using a hostname, the request might be rejected by host header validation. If the hostname is legitimate, declare it as a server alias.

Satellite validates the HTTP Host header on every incoming request. Only requests whose Host header matches the server FQDN or a declared server alias are accepted. Requests that use an IP address, a short hostname, or any other undeclared name are rejected with a 403 Forbidden error.

Procedure

  1. Confirm that the error is a 403 Forbidden response from your Satellite Server:

    $ curl --head --insecure https://hostname.example.com
    HTTP/1.1 403 Forbidden

  2. Verify that host header validation caused the rejection by checking the Satellite Server journal for the blocked-host message:

    # journalctl --unit foreman --reverse --lines 5 --grep "Blocked hosts"
    Example output
    Jul 15 21:49:28 satellite.example.com foreman[52746]: 2026-07-15T21:49:28 [E|app|] [ActionDispatch::HostAuthorization::DefaultResponseApp] Blocked hosts: hostname.example.com, hostname.example.com

  3. Retrieve the FQDN and any server aliases that Satellite Server currently accepts:

    # hostname --fqdn
    # podman secret inspect foreman-settings-yaml --showsecret --format "{{.SecretData}}" | grep ":hosts:" --after-context=3

    If hostname.example.com does not appear in either output, host header validation is rejecting the request.

  4. Resolve the problem:

    • If hostname.example.com is a legitimate alternate name for your Satellite Server, declare it as a server alias.

    • If hostname.example.com is not a name you expect your Satellite to answer, the request might indicate a misconfiguration in your network or a security concern. Open a Red Hat Support case for further investigation.

Verification

  • After you configure a server alias, verify that the request succeeds:

    $ curl --silent https://hostname.example.com/api/v2/ping | python3 -m json.tool

    The request returns JSON with service status information.

3. Troubleshoot content issues

Diagnose and identify root causes when Satellite content management operations fail or behave unexpectedly.

3.1. Recover corrupted content

When content corruption causes synchronization failures or checksum mismatches, you can resynchronize repositories, verify checksums, and republish metadata to restore repository integrity and ensure hosts can reliably access packages.

3.1.1. Recover a corrupted repository by using Satellite web UI

Recover a corrupted repository with optimized or complete advanced sync, and optionally verify content checksums to confirm packages match upstream sources.

Procedure

  1. In the Satellite web UI, navigate to Content > Products.

  2. Select the product containing the corrupted repository.

  3. Select the name of a repository you want to synchronize.

  4. To perform optimized sync or complete sync, select Advanced Sync from the Select Action menu.

  5. Select the required option and click Sync.

  6. Optional: To verify the checksum for a Yum repository, click Verify Content Checksum from the Select Action menu.

3.1.2. Recover a corrupted repository by using Hammer CLI

Recover a corrupted repository by using optimized sync, complete sync, or validate-content synchronization when packages or metadata no longer match expected content.

Procedure

  1. Obtain a list of repository IDs:

    $ hammer repository list \
--organization "My_Organization"

  2. Synchronize a corrupted repository using the necessary option:

    • For the optimized synchronization:

      $ hammer repository synchronize \
--id My_ID

    • For the complete synchronization:

      $ hammer repository synchronize \
--id My_ID \
--skip-metadata-check true

    • For validating content of a Yum repository:

      $ hammer repository synchronize \
--id My_ID \
--validate-contents true

3.1.3. Recover corrupted content on a Capsule Server by using Satellite web UI

Verify checksums for a lifecycle environment or content view on your Capsule Server when hosts cannot consume content and you need to repair corrupted files on the Capsule Server.

Procedure

  1. In the Satellite web UI, navigate to Infrastructure > Capsules.

  2. Select your Capsule Server.

  3. Recover corrupted content on your Capsule Server.

    • To repair content in a lifecycle environment, click the options menu icon next to your lifecycle environment and select Verify Content Checksum.

    • To repair content in a content view, click the options menu icon next to your content view and select Verify Content Checksum.

Verification

  1. In the Satellite web UI, navigate to Monitor > Satellite Tasks > Tasks.

  2. Search for Verify checksum for content.

  3. Verify that the task completed successfully.

3.1.4. Recover corrupted content on a Capsule Server by using CLI

Verify checksums on your Capsule Server for a repository, content view, lifecycle environment, or all Capsule Server content when hosts cannot consume synchronized packages.

Prerequisites

  • The lifecycle environment, content view, or repository that you want to repair is available on the Capsule Server.

Procedure

  1. Display a list of all Capsules:

    $ hammer capsule list

    Note the ID of your Capsule Server.

  2. Recover corrupted content on your Capsule Server:

    • Repair content in a content view:

      $ hammer capsule content verify-checksum \
--content-view-id My_Content_View_ID \
--id My_Capsule_Server_ID \
--organization-id My_Organization_ID

    • Repair content in a lifecycle environment:

      $ hammer capsule content verify-checksum \
--id My_Capsule_Server_ID \
--lifecycle-environment-id My_Lifecycle_Environment_ID \
--organization-id My_Organization_ID

    • Repair content in a repository:

      $ hammer capsule content verify-checksum \
--id My_Capsule_Server_ID \
--organization-id My_Organization_ID \
--repository-id My_Repository_ID

    • Repair all content on your Capsule Server:

      $ hammer capsule content verify-checksum \
--id My_Capsule_Server_ID
Verification

  • Verify that the task completed successfully:

    $ hammer task list --search "Verify checksum for content"

3.1.5. Republish repository metadata by using Satellite web UI

Republish repository metadata when published metadata does not match repository contents.

Warning

Red Hat recommends a complete repository sync or publishing a new content view version to repair broken metadata instead.
Prerequisites

  • The mirroring policy of the repository is not set to Complete Mirroring.

    This action is not available for repositories that use the Complete Mirroring policy because the metadata is copied verbatim from the upstream source of the repository.

Procedure

  1. In the Satellite web UI, navigate to Content > Products.

  2. Select the product that includes the repository for which you want to republish metadata.

  3. On the Repositories tab, select a repository.

  4. To republish metadata for the repository, click Republish Repository Metadata from the Select Action menu.

3.1.6. Republish repository metadata by using CLI

Republish repository metadata when published metadata does not match repository contents.

Warning

Red Hat recommends a complete repository sync or publishing a new content view version to repair broken metadata in favor of republishing repository metadata.
Prerequisites

  • The mirroring policy of the repository is not set to Complete Mirroring.

    This action is not available for repositories that use the Complete Mirroring policy because the metadata is copied verbatim from the upstream source of the repository.

Procedure

  • Republish metadata for your repository:

    $ hammer repository verify-checksum \
--name "My_Repository_Name" \
--organization-id My_Organization_ID \
--product "My_Product_Name"
Verification

  • Verify that the task completed successfully:

    $ hammer task list --search "Metadata generate repository"

3.1.7. Republish content view metadata by using Satellite web UI

Republish content view version metadata when hosts report checksum mismatches. Satellite can regenerate metadata for repositories that do not use complete mirroring.

Republishing regenerates metadata for all repositories in the content view version that do not adhere to the Complete Mirroring policy.

Prerequisites

  • The content view version includes repositories that do not use the Complete Mirroring policy.

Procedure

  1. In the Satellite web UI, navigate to Content > Lifecycle > Content Views.

  2. Select a content view.

  3. On the Versions tab, select a content view version.

  4. To republish metadata for the content view version, click Republish repository metadata from the options icon.

3.1.8. Republish content view metadata by using CLI

Republish content view version metadata when hosts report checksum mismatches. Satellite can regenerate metadata for repositories that do not use complete mirroring.

Republishing regenerates metadata for all repositories in the content view version that do not adhere to the Complete Mirroring policy.

Prerequisites

  • The content view version includes repositories that do not use the Complete Mirroring policy.

Procedure

  • Republish metadata for your content view version:

    $ hammer content-view version verify-checksum --id My_Content_View_Version_ID

4. Gather diagnostic information for support

Gather comprehensive diagnostic information to provide Red Hat Support with the data required for troubleshooting Satellite issues.

4.1. Manage logs for Satellite

With centralized logging, you can monitor Satellite service health, diagnose errors, and control log retention and disk usage in a single interface. You can also collect diagnostic data and attach it to support cases.

4.1.1. Satellite logging architecture

Satellite Server manages all service logs by using a centralized system built on systemd and journald. Instead of searching through separate log files in different directories, you can manage all service activity from a single pipeline.

All Satellite services send their log output to stdout by default. The container runtime automatically captures this data stream and passes it to the logging daemon.

You interact with the logging architecture through the following key components:

  • With the journald service, you collect and store all service logs in one place. By default, you lose log history when the system reboots as journald stores log data in volatile memory. You can configure journald to store logs in persistent storage so that you can retain log history across system restarts.

    For details on configuring the journald service, see the official Red Hat Enterprise Linux documentation.

  • With journalctl, you can view, search, and filter logs for any service from a single interface without opening individual log files.

  • Use the satellitectl deploy command to change log levels or adjust logging verbosity.

For additional help, you can contact Red Hat Technical Support. Use the sos utility to collect configuration and diagnostic data from your system and provide the files with your support case.

4.1.2. View service logs

You can view and filter logs for any Satellite service by using journalctl with the appropriate unit filter. Use correlation IDs to trace a single request across multiple services such as Foreman and Pulp.

Prerequisites

  • Satellite Server is installed and running.

  • You have root access to your Satellite Server.

Procedure

  • To view logs for a specific service:

    # journalctl --unit My_Service

  • To follow log output in real time, add the --follow flag:

    # journalctl --follow --unit My_Service

    For example:

    # journalctl --follow --unit foreman

    Example output:

    Aug 10 07:19:29 satellite.example.com foreman[1632]: 2026-08-10T07:19:29 [I|app|eb515c9c] Started GET "/api/v2/ping" for 192.168.124.1
Aug 10 07:19:29 satellite.example.com foreman[1632]: 2026-08-10T07:19:29 [I|app|eb515c9c] Processing by Api::V2::PingController#ping as JSON
Aug 10 07:19:29 satellite.example.com foreman[1632]: 2026-08-10T07:19:29 [I|app|eb515c9c] Completed 200 OK in 186ms (Views: 12.8ms | ActiveRecord: 8.1ms | Allocations: 42460)

    In this output, eb515c9c is the correlation ID.

  • To trace a request across services, locate the correlation ID in the log output and filter by it:

    # journalctl --grep My_Correlation_ID

    For example:

    # journalctl --grep eb515c9c

    Example output:

    Aug 10 07:19:29 satellite.example.com foreman[1632]: 2026-08-10T07:19:29 [I|app|eb515c9c] Started GET "/api/v2/ping" for 192.168.124.1
Aug 10 07:19:29 satellite.example.com foreman[1632]: 2026-08-10T07:19:29 [I|app|eb515c9c] Processing by Api::V2::PingController#ping as JSON
Aug 10 07:19:29 satellite.example.com pulp-api[1193]: pulp [eb515c9c-cb85-44fa-bd6e-c49eaab71bc5]: "GET /pulp/api/v3/status/ HTTP/1.1" 200 6250
Aug 10 07:19:29 satellite.example.com foreman[1632]: 2026-08-10T07:19:29 [I|app|eb515c9c] Completed 200 OK in 186ms (Views: 12.8ms | ActiveRecord: 8.1ms | Allocations: 42460)
Verification

  • Verify that the command returns log entries for the expected service:

    # journalctl --unit My_Service -n 5

4.1.3. Set service log levels

You can set the log level for Satellite services by using satellitectl deploy parameters.

At the initial deployment, when the containers are first created, the log level is set to the default value of info. You can change the log level for all services or for individual services.

Procedure

  • To set the global log level for all supported services, run:

    # satellitectl deploy --log-level Log_Level

    For example, to set the global log level to debug, run:

    # satellitectl deploy --log-level debug

  • To override the log level for a specific service, use a service-specific parameter, such as --foreman-log-level and --foreman-proxy-log-level.

    For example, to set only Foreman to error while keeping other services at the global level, run:

    # satellitectl deploy --foreman-log-level error

    After you complete debugging, reset the log level to the default to avoid filling up host disk space:

    # satellitectl deploy --reset-foreman-log-level
    Note

    Each service inherits the default value from the log-level parameter, unless you set the value for the service by using the My_Service-log-level parameter. Running foremanctl deploy --log-level New_Log_Level or foremanctl deploy --reset-log-level does not affect the --My_Service-log-level parameters.
Verification

  • Verify that a new log level took effect as actions occur:

    # journalctl --unit foreman --follow
Additional resources

  • Log level parameters

Log level parameters

You can control the log detail level of containerized Satellite services with the satellitectl deploy log level parameters.

The --log-level parameter sets the global baseline for all services. The valid values are: debug, info, warn, error, fatal out of which info is the default.

Per-service parameters override this value and translate it to the native vocabulary of each service:

--foreman-log-level

Foreman service. Values: debug, info, warn, error, fatal.

--foreman-proxy-log-level

Foreman Proxy. Values: debug, info, warn, error, fatal.

--pulp-log-level

Pulp services (pulpcore-api, pulpcore-content, pulpcore-worker). Values: debug, info, warning, error, critical.

--valkey-log-level

Valkey. Independent of --log-level. Values: debug, verbose, notice, warning, nothing. Default: notice.

These services do not have dedicated satellitectl deploy log level parameters and are not affected by the global --log-level parameter:

  • Candlepin

  • PostgreSQL

  • httpd

5. Anonymize audit records

You can anonymize audit records to remove user account and IP information while preserving the audit trail. This is useful for maintaining compliance with privacy regulations or internal security policies.

Procedure

  • Use the foreman-rake audits:anonymize command to remove any user account or IP information while maintaining the audit records in the database. Specify the number of days to keep the audit records by adding the days option and add the number of days. You can also use a cron job to schedule anonymizing the audit records at the set interval that you want.

    For example, you can anonymize audit records that are older than seven days:

    # foreman-rake audits:anonymize days=7

6. Diagnose and resolve Red Hat Lightspeed issues

Troubleshoot Red Hat Lightspeed issues to diagnose and resolve problems when the service does not work as expected.

6.1. Diagnose hosted Red Hat Lightspeed

You can troubleshoot issues with Red Hat Lightspeed in the Red Hat Hybrid Cloud Console by checking logs and certificates.

To troubleshoot hosts monitoring, you can try the following approaches:

  • View the logs for all Red Hat Lightspeed in Satellite services:

    # journalctl --unit "iop*"

    The names of all Red Hat Lightspeed in Satellite services have the iop prefix.

    For the full list of commands to view and filter service logs, such as following log output in real time or tracing a request by its correlation ID, see Viewing service logs.

  • View the logs for a specific service unit:

    # journalctl --unit iop-service-unit

  • If you have problems connecting to Red Hat Lightspeed, ensure that your certificates are current. Refresh your subscription manifest to update your certificates.

6.2. Diagnose Red Hat Lightspeed in Satellite

You can check the logs to troubleshoot issues with Red Hat Lightspeed in Satellite.

The names of all Red Hat Lightspeed in Satellite services have the iop prefix. To view the logs for all Red Hat Lightspeed in Satellite services, enter the following command:

# journalctl --unit "iop*"

For the full list of commands to view and filter service logs, such as following log output in real time or tracing a request by its correlation ID, see Viewing service logs.

If you expect new CVEs but do not see them on the Vulnerability page, consider updating the vulnerability metadata by synchronizing. You can trigger a scan by synchronizing a repository. When you update a host, Satellite pulls any missing CVEs during vulnerability evaluation. If you need to refresh the metadata manually, you can start the vulnerability metadata download service:

# systemctl start iop-vuln-metadata-download.service
Note

The download service relies on a single-threaded scan. If synchronization is already in progress, the service might fail or time out.

7. Resolve Satellite login failures

Diagnose and resolve authentication problems in Satellite when users cannot log in, external authentication sources fail to connect, or user group synchronization does not work as expected.

7.1. Reset the administrative user password

You can reset the administrative password to randomly generated characters or set a new administrative password for a specific user. This might be useful when you forget the password, when the administrative user is deleted, or for assigning administrative privileges to a user.

Procedure

  1. Log in to the base operating system where your Satellite Server is installed.

  2. Reset the administrative user password:

    • To set a randomly generated administrative user password:

      # foreman-rake permissions:reset
Reset to user: admin, password: qwJxBptxb7Gfcjj5

    • To set a new administrative user password:

      # foreman-rake permissions:reset username=My_User_Name password=My_New_Password

      Replace My_User_Name with the username of the user whose password you want to reset.

      Note

      Be aware of the following behaviors:

      • If you enter a username that does not exist, the foreman-rake utility creates a new administrative user with the defined password.

      • If you enter a username of a user without administrative privileges, that user gains administrative privileges.

      • If you do not enter a username, the password resets for the admin user by default.

  3. To use the new password with the Hammer CLI, add the password and username to the ~/.hammer/cli.modules.d/foreman.yml file on your Satellite Server:

    # vi ~/.hammer/cli.modules.d/foreman.yml
Verification

  • Use the new password to log in to the Satellite web UI.

7.2. Refresh external user groups for LDAP using Satellite web UI

You can refresh external user groups manually if you want to immediately update membership changes from your LDAP source.

To set the LDAP source to synchronize user group membership automatically on user login, in the Auth Source page, select the Usergroup Sync option. If this option is not selected, LDAP user groups are refreshed automatically every hour by default.

If the user groups in the LDAP Authentication source change in the lapse of time between scheduled tasks, the user can be assigned to incorrect external user groups. This is corrected automatically when the scheduled task runs.

Procedure

  1. In the Satellite web UI, navigate to Administer > Usergroups and select a user group.

  2. On the External Groups tab, click Refresh to the right of the required user group.

8. Fix remote jobs that cannot resolve the host name

If remote execution jobs fail on your host due to Could not resolve hostname: Name or service not known, disable Ignore interfaces facts for provisioning.

Procedure

  1. In the Satellite web UI, navigate to Hosts > All Hosts.

  2. Select your host.

  3. Click Edit.

  4. On the Interfaces tab, check if the host has an IP address. If the host has no IP address, continue with this procedure.

  5. Navigate to Administer > Settings.

  6. On the Facts tab, set Ignore interfaces facts for provisioning to No. This ensures that an IP address is assigned to the host during registration.

= Puma workers and threads recommendations

[role="_abstract"]
These recommendations are based on performance testing with concurrent host registrations across different deployment sizes.
Use these test results to make informed decisions about worker and thread counts for your specific deployment size and workload patterns.

The main test was concurrent registration with different numbers of workers and threads.
These recommendations focus on concurrent registration performance and might not match your exact use case.
ifdef::katello,orcharhino,satellite[]
For example, if your setup focuses on content with many publishes and promotes, limit Puma resources to favor Pulp and PostgreSQL.
endif::[]

[width="100%",cols="16%,19%,7%,7%,31%,20%",options="header",]
|===
|Name |Number of hosts |RAM |Cores |Recommended Puma threads |Recommended Puma workers
|default |0{range}5000 |20 GiB |4 |16 |4{range}6
|medium |5000{range}10000 |32 GiB |8 |16 |8{range}12
|large |10000{range}20000 |64 GiB |16 |16 |12{range}18
|extra-large |20000{range}60000 |128 GiB |32 |16 |16{range}24
|extra-extra-large |60000+ |256 GiB+ |48+ |16 |20{range}26
|===

Worker count is more important than thread count.
We have seen up to 52% performance increase by adjusting workers.
Although the installer uses 5 threads by default, we recommend 16 threads with all the tuning profiles in the table above.
We have seen up to 23% performance increase with 16 threads (14% for 8 and 10% for 32) compared to 4 threads.

These recommendations use concurrent registrations as the test case.
Your {Project} might have different workloads, such as more balanced operations beyond registrations.
The default 5 threads is also a good choice.

These are some of our measurements that lead us to these recommendations:

[width="100%",cols="17%,21%,20%,21%,21%",options="header",]
|===
| |4 workers, 4 threads |4 workers, 8 threads |4 workers, 16 threads |4 workers, 32 threads
|Improvement| 0%| 14%| 23%| 10%
|===

Use 4{range}6 workers on a default setup (4 CPUs).
We have seen 25% better performance with 5 workers versus 2 workers.
However, 8 workers performed 8% worse than 2 workers.
See the table below:

[width="100%",cols="17%,21%,20%,21%,21%",options="header",]
|===
| |2 workers, 16 threads |4 workers, 16 threads |6 workers, 16 threads |8 workers, 16 threads
|Improvement |0% |26% |22% |-8%
|===

Use 8{range}12 workers on a medium setup (8 CPUs) {endash} see table below:

[width="100%",cols="16%,17%,16%,17%,17%,17%",options="header",]
|===
| |2 workers, 16 threads |4 workers, 16 threads |8 workers, 16 threads |12 workers, 16 threads |16 workers, 16 threads
|Improvement |0% |51% |52% |52% |42%
|===

Use 16{range}24 workers on a 32 CPU setup.
This was tested on a 90 GiB RAM machine.
Memory became a factor as the system started swapping.
An _extra-large_ setup should have 128 GiB.
More workers caused problems at higher registration concurrency levels, so we do not recommend it.

[width="100%",cols="13%,14%,14%,14%,15%,15%,15%",options="header",]
|===
| |4 workers, 16 threads |8 workers, 16 threads |16 workers, 16 threads |24 workers, 16 threads |32 workers, 16 threads |48 workers, 16 threads
|Improvement |0% |37% |44% |52% |too many failures |too many failures
|===
